Topic 01 • Architecture

How Databases Execute Queries

■ What is it?
The internal query processing pipeline that translates a declarative SQL text string into an imperative physical execution tree executed against the memory buffer pool and physical storage.
■ Why does it exist?
SQL tells the engine what data to produce, not how to retrieve it. The database engine must validate grammar, resolve catalog metadata, evaluate millions of algorithmic permutations, size memory grants, and manage disk I/O asynchronously.
■ How does it work?

The query lifecycle progresses through five distinct sub-systems:

  1. Parser & Lexer: Tokenizes the character stream and constructs an Abstract Syntax Tree (AST) verifying grammar rules in microseconds without catalog locks.
  2. Semantic Binder / Catalog Resolver: Queries the data dictionary to verify object existence (tables, views, columns), enforce user permissions, and bind data types.
  3. Query Optimizer (RBO & CBO): Applies logical rewrites (Predicate Pushdown, Projection Pruning, Constant Folding) and uses cost models (I/O, CPU, RAM) parameterized by histograms to pick the lowest-cost physical plan.
  4. Execution Engine (Volcano / Vectorized Engine): Executes the physical plan via iterator pipelines (open(), next(), close()) or columnar SIMD vectorized batches.
  5. Storage Engine & Buffer Manager: Manages 8KB page caching in RAM (Buffer Pool). If a page is cached (Cache Hit), it reads directly from RAM; otherwise, it triggers asynchronous storage reads.
■ Visual explanation
SQL Query Text ──► [Lexer / Parser] ──► Abstract Syntax Tree (AST) │ ▼ [Semantic Binder / Catalog] ──► Bound Logical Tree │ ▼ [Optimizer (RBO + CBO)] ──► Physical Plan (Tree of Iterators) │ ▼ [Execution Engine (Volcano)] ──► open() / next() / close() │ ▼ [Buffer Pool Manager] ──► RAM Cache Hit vs Asynchronous Disk I/O │ ▼ Tabular Stream Output
💡 Analogy
Submitting SQL is like ordering at a restaurant. You describe the dish on a ticket (SQL). The waiter checks spelling and pantry stock (Parser & Binder). The head chef evaluates cooking techniques and timing (Optimizer). The line cooks follow the recipe card (Execution Engine), pulling raw ingredients from the walk-in freezer (Storage Engine).
■ Symptoms High CPU with zero I/O waits; queries with 1ms execution taking 50ms total latency; plan cache memory exhaustion.
■ How to diagnose it Compare Compilation/Parse time vs Execution runtime using pg_stat_statements (Postgres) or sys.dm_exec_query_stats (SQL Server).
■ How to fix it Enforce Parameterized Prepared Statements to parse/bind once and reuse cached execution plans across executions.
■ Common mistakes Believing the database executes SQL top-to-bottom imperatively; concatenating raw strings in ORMs forcing repeat compilation.
■ Production considerations
In high-throughput OLTP systems (10k+ QPS), compilation CPU overhead can exceed execution CPU. Prepared statements eliminate compilation latency but risk Parameter Sniffing on skewed datasets.
30-Second Interview Answer ⏱️ Recall
"Query execution follows a five-stage lifecycle: the parser tokenizes SQL into an AST for grammar check; the binder resolves catalog metadata, types, and permissions; the optimizer applies rule-based logical rewrites and cost-based physical operator selection using histograms; the execution engine processes tuples via Volcano iterators or vectorized batches; and the storage engine coordinates buffer pool memory hits and asynchronous disk page fetches."
Interviewer Follow-Up: What is the difference between compile time and run time? ▼
Answer: Compile time is purely CPU-bound in-memory work (parsing grammar, resolving metadata, exploring join permutations, and computing cost models). Run time encompasses disk I/O, memory grant buffer allocations, lock acquisitions, CPU tuple evaluations, and network serialization over wire protocol.
🔑 Key Takeaway: SQL is declarative intent. The engine translates intent into an imperative physical iterator tree executed against the RAM buffer pool.
Topic 02 • Access Paths

Indexing: B-Trees, Clustered & Covering Indexes

■ What is it?
Auxiliary B+ Tree data structures that maintain sorted key pointers to enable $O(\log N)$ point seeks and range scans instead of $O(N)$ sequential table scans.
■ Why does it exist?
Without indexes, finding a single record in a 100-million row table requires reading every single 8KB storage block from disk (gigabytes of I/O). An index reduces this to 3–4 page reads.
■ How does it work?
  • B+ Tree Internals: Balanced multi-way search tree. Root page branches to intermediate pages, which point to doubly linked Leaf pages. Leaf pages hold sorted index keys.
  • Clustered Index: The table is the index. Leaf pages contain the actual physical data rows sorted by the clustered key (1 per table).
  • Non-Clustered (Secondary) Index: Leaf pages contain index keys plus a bookmark pointer (Clustered Key or RID heap pointer) to locate the base row.
  • Covering Index & Included Columns: An index containing all columns requested in SELECT, WHERE, and JOIN clauses. Using INCLUDE(colA, colB) stores payload columns in the leaf level without widening intermediate B-Tree branch nodes, enabling pure Index-Only Scans with zero bookmark lookups.
  • Composite Index & The ESR Rule: Multi-column index (A, B, C) sorted hierarchically. Follows the Equality-Sort-Range order: place Equality columns first, then Sort/Range columns.
■ Visual explanation
[ Root B-Tree Node ] / [ Branch Node 1..500 ] [ Branch Node 501..1000 ] / \ / [ Leaf: 1..250 ] [ Leaf: 251..500 ] [ Leaf: 501..750 ] [ Leaf: 751..1000 ] └──► Contiguous doubly-linked list for lightning-fast range scans ◄──┘ Non-Clustered Index Seek: [Index Leaf Page] ──(Find Match)──► [Bookmark Lookup / Key Lookup] ──► [Base Data Heap Page] (Random I/O) Covering Index Seek (Index-Only Scan): [Index Leaf Page with INCLUDE columns] ──(Contains All Required Data!)──► Direct Output Stream (0 Random Lookups!)
■ Symptoms High random I/O waits (PAGEIOLATCH); excessive Key Lookups / Bookmark Lookups consuming 95% of plan cost.
■ How to diagnose it Look for Key Lookup (Clustered) or RID Lookup operators nested inside a loop in the execution plan.
■ How to fix it Add missing payload columns to the secondary index definition using INCLUDE (col1, col2) to convert the lookup into a covering Index-Only Scan.
■ Common mistakes Adding 10 columns to index key definitions (bloating branch nodes); indexing low-cardinality boolean columns; ignoring composite column ordering.
■ Production considerations
Every index accelerates reads but imposes a write penalty on INSERT, UPDATE, and DELETE due to B-Tree page splits and write amplification. Clustered index keys should always be narrow, static, and monotonically increasing (e.g. BIGINT IDENTITY) to avoid random page splits.
30-Second Interview Answer ⏱️ Recall
"A clustered index defines the physical sorting order of the table rows at the leaf level, while a non-clustered index stores sorted key columns and bookmark row pointers. In performance tuning, we design composite indexes following the Equality-Sort-Range rule and leverage covering indexes with INCLUDE columns to enable Index-Only Scans, eliminating expensive random bookmark lookups into the base heap."
Interviewer Follow-Up: Why should we use INCLUDE instead of adding columns to the index key? ▼
Answer: Adding columns to the index key widens the key size on all root, intermediate, and leaf B-Tree pages, reducing the fanout factor and increasing B-Tree depth. INCLUDE columns are stored strictly at the leaf level, preserving a compact, high-fanout B-Tree branch structure while achieving full index coverage.
🔑 Key Takeaway: Eliminate random I/O bookmark lookups by turning secondary index seeks into Covering Index-Only Scans with the ESR rule and INCLUDE columns.
Topic 03 • Predicate Optimization

SARGability: Writing Search-Argument-Able Queries

■ What is it?
SARGable (Search-Argument-Able) predicates are filter conditions written so that the query engine can directly navigate a B-Tree index using root-to-leaf binary range seeks rather than scanning every row.
■ Why does it exist?
B-Trees are sorted by raw, untransformed column values. If a query modifies the indexed column with a function, arithmetic, or implicit type conversion, the engine cannot determine range boundaries and is forced into a full table scan.
■ How does it work? (4 Core Anti-Patterns & Exact Rewrites)
-- 1. FUNCTIONS ON COLUMNS
-- ❌ Non-SARGable:
SELECT * FROM orders WHERE YEAR(order_date) = 2024;
-- ✅ SARGable Rewrite:
SELECT * FROM orders WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01';

-- 2. LEADING WILDCARDS
-- ❌ Non-SARGable:
SELECT * FROM customers WHERE email LIKE '%@gmail.com';
-- ✅ SARGable Rewrite (or reverse-indexed):
SELECT * FROM customers WHERE email LIKE 'john.doe@%';
-- (Or use Full-Text Search / Reverse Index for suffix matching: WHERE reverse_email LIKE 'moc.liamg@%')

-- 3. IMPLICIT TYPE CASTS (e.g. phone is VARCHAR, passing INT)
-- ❌ Non-SARGable:
SELECT * FROM users WHERE phone_number = 9876543210; -- Engine converts col: CAST(phone_number AS BIGINT)
-- ✅ SARGable Rewrite:
SELECT * FROM users WHERE phone_number = '9876543210';

-- 4. ARITHMETIC ON COLUMNS
-- ❌ Non-SARGable:
SELECT * FROM products WHERE price * 0.9 > 100;
-- ✅ SARGable Rewrite:
SELECT * FROM products WHERE price > (100 / 0.9);
■ Visual explanation
Non-SARGable Predicate: WHERE UPPER(last_name) = 'SMITH' B-Tree Leaf: ['Adams', 'Baker', 'Clark', ... 'Smith', ... 'Zimmerman'] └──► Engine CANNOT do binary search for 'SMITH' because keys are mixed-case! Must read all 10,000,000 leaf entries and evaluate UPPER() row-by-row. SARGable Predicate: WHERE last_name >= 'Smith' AND last_name < 'Smiti' B-Tree Root ──► Intermediate Node ──► Binary seeks directly to 'Smith' in 3 page reads!
■ Symptoms Index exists on column, but execution plan shows Table Scan or Seq Scan taking 20+ seconds.
■ How to diagnose it Inspect execution plan filter text. Look for CONVERT_IMPLICIT or scalar function wrappers around the indexed column name.
■ How to fix it Isolate the indexed column completely on one side of the operator: column_name OPERATOR constant_expression.
■ Common mistakes Using DATE(col) = '2024-01-01'; matching numbers to string columns; writing WHERE col + 7 > CURRENT_DATE.
■ Production considerations
If business logic requires querying transformed values frequently (e.g. case-insensitive lookups), create a Functional / Expression Index: CREATE INDEX idx_user_lower ON users (LOWER(username));.
30-Second Interview Answer ⏱️ Recall
"SARGability means writing predicates so the engine can perform direct B-Tree index seeks. The four primary anti-patterns that destroy SARGability are: wrapping columns in scalar functions, using leading wildcards in LIKE clauses, performing arithmetic on column expressions, and triggering implicit type conversions. We fix these by isolating the raw column and expressing criteria as half-open range bounds."
Interviewer Follow-Up: How does implicit type casting break SARGability in SQL Server? ▼
Answer: SQL Server applies strict Data Type Precedence rules. Because INT has higher precedence than VARCHAR, comparing WHERE varchar_col = 123 forces the engine to inject an implicit CONVERT_IMPLICIT(int, varchar_col) wrapper around the column for every row, disabling index seeks and forcing a full scan.
🔑 Key Takeaway: Always isolate raw indexed columns on one side of the operator: `indexed_col >= constant_start AND indexed_col < constant_end`.
Topic 04 • Metadata & Costing

Statistics, Histograms & Cardinality Estimation

■ What is it?
Statistical metadata stored in the catalog—including row counts, page counts, null fractions, Number of Distinct Values (NDV), and Equi-Height Histograms—used by the optimizer to predict the number of rows (cardinality) emitted by every query operator.
■ Why does it exist?
The optimizer cannot scan table rows during compilation. It needs mathematical distributions to decide between Index Seeks vs Scans, Nested Loops vs Hash Joins, and to size memory grants for hashing and sorting.
■ How does it work?
  • Equi-Height (Equal-Depth) Histograms: The database sorts column values into buckets containing an equal number of rows. Bucket boundaries dynamically adjust to capture data density and data skew accurately.
  • Most Common Values (MCV): Lists the most frequent individual values and their exact percentages.
  • Estimated vs Actual Rows: The optimizer estimates rows at compile time. At runtime, the execution engine tracks actual rows. A large divergence ($>10 imes$ or $<0.1 imes$) causes the Cardinality Error Cascade.
  • The Independence Trap: By default, optimizers assume multi-column filters are independent: $Sel(A \land B) = Sel(A) imes Sel(B)$. On correlated data (e.g. State = 'CA' AND City = 'SF'), this causes severe underestimation.
■ Visual explanation
Equi-Height Histogram (1,000,000 Rows, 5 Buckets = 200,000 rows/bucket): [ Bucket 1: $0..$15 ] [ Bucket 2: $15..$45 ] [ Bucket 3: $45..$120 ] [ Bucket 4: $120..$350 ] [ Bucket 5: $350..$9500 ] The Cardinality Error Cascade: Filter Node: [Est: 1 row | Actual: 250,000 rows] (Independence assumption failure) │ ▼ Join Node: Optimizer picks Nested Loops (expecting 1 seek) ──► 💥 250,000 iterations! │ ▼ Sort Node: Memory Grant sized for 1 row (1MB) ──► 💥 Spills 500MB to TempDB / Workfiles!
■ Symptoms ETL query slows from 2 minutes to 40 minutes after bulk loading; severe disk spills to TempDB/workfiles; Nested Loops running endlessly.
■ How to diagnose it In EXPLAIN ANALYZE, compare Estimated Rows vs Actual Rows at each node. Check last_analyze timestamp in catalog.
■ How to fix it Run ANALYZE table_name; or create Extended Multi-Column Statistics: CREATE STATISTICS s_geo ON city, state FROM customers;.
■ Common mistakes Ignoring stats updates after bulk data loads; assuming the optimizer knows columns are correlated without multi-column statistics.
■ Production considerations
Auto-analyze triggers when modifications exceed a percentage threshold (e.g. 10–20%). On massive 500M row tables, a 10% change is 50M rows—meaning stats remain stale for weeks unless explicit post-ETL analysis is scheduled in pipelines.
30-Second Interview Answer ⏱️ Recall
"Statistics and histograms are the metadata eyes of the cost-based optimizer, providing row counts, distinct values, and equi-height data distributions. Cardinality estimation errors—frequently caused by stale statistics or correlated predicates violating independence assumptions—cascade up the execution tree, causing the optimizer to select disastrous Nested Loop joins and undersized memory grants that spill to disk."
Interviewer Follow-Up: How do you fix correlated predicate underestimation in PostgreSQL? ▼
Answer: By creating Extended Statistics using CREATE STATISTICS stat_name (dependencies, mcv) ON col1, col2 FROM table; followed by ANALYZE table;. This instructs the engine to build multi-column histograms and track dependency coefficients.
🔑 Key Takeaway: Estimated Rows vs Actual Rows is the #1 tuning diagnostic. Stale stats or correlated columns cause memory spills and loop thrashing.
Topic 05 • Plan Profiling

Execution Plans: Reading, Operators & Plan Analysis

■ What is it?
The compiled physical operator tree produced by the optimizer. EXPLAIN displays compile-time estimates, while EXPLAIN ANALYZE executes the query to return true runtime wall-clock duration, memory grants, and buffer I/O hits.
■ Why does it exist?
It is the definitive X-ray of query execution, revealing exactly where bottlenecks (disk I/O, hash spills, full scans, Cartesian loops) occur in production.
■ How does it work? (Core Operator Breakdown)
  • Sequential Scan / Table Scan: Reads all contiguous 8KB pages from start to finish. Fast for large analytical aggregations, disastrous for point lookups.
  • Index Scan vs Index Seek: Index Seek navigates B-Tree root-to-leaf in $O(\log N)$. Index Scan reads all leaf pages of the index in sorted order.
  • Bitmap Index Scan + Bitmap Heap Scan (Postgres): Creates an in-memory bitmap of matching physical page blocks from the index, sorts physical page numbers, and reads heap pages in sequential I/O order, avoiding random I/O thrashing.
  • Nested Loops Join: Iterates outer rows and executes inner lookups. Ideal for tiny outer driving tables (<100 rows).
  • Hash Join: Hashes the smaller build relation in RAM, then streams and probes the larger relation. $O(M+N)$ linear complexity.
  • Merge Join: Merges two pre-sorted input streams in lockstep with minimal memory overhead.
  • Sort vs Top-N Sort: Explicit Sort requires $O(N \log N)$ memory workspace. Top-N Sort uses an in-memory priority queue of size $K$ for ORDER BY ... LIMIT K queries.
■ Visual explanation: How to Read an Execution Plan
Rule for Reading Plans: Read from INNERMOST INDENTATION to OUTERMOST (Bottom-Up, Inside-Out). Hash Join (Cost: 450.0..1200.0, Rows: 5000, Actual Time: 12.4ms) ├── 1. Build Phase: Seq Scan on customers (Filter: country = 'US') -> Builds Hash Map in RAM └── 2. Probe Phase: Seq Scan on orders (Filter: date >= 2024) -> Streams rows & probes Hash Map Red Flag Checklist when reading plans: 1. Discrepancy: Est Rows = 1 vs Actual Rows = 500,000. 2. Operator: Nested Loops with 5,000,000 actual loop executions. 3. Disk Spills: "Sort Method: external merge Disk: 450MB" or "Hash Join Spill Level 1". 4. Filter above Join: Predicate pushdown failure.
■ Symptoms Query latency exceeds SLA; high storage queue depth; high memory churn.
■ How to diagnose it Run EXPLAIN (ANALYZE, BUFFERS, VERBOSE) in Postgres or capture graphical plan with Runtime Metrics in SQL Server / Databricks Spark UI.
■ How to fix it Identify the single operator node consuming 80%+ of total execution cost/time and apply targeted indexing, rewrites, or memory grants.
■ Common mistakes Reading plans top-to-bottom instead of inside-out; focusing on estimated cost percentages instead of actual runtime duration and row count deltas.
■ Production considerations
Never run EXPLAIN ANALYZE on a production DELETE or UPDATE statement without wrapping it in a rolled-back transaction (BEGIN; EXPLAIN ANALYZE DELETE ...; ROLLBACK;), as ANALYZE actually executes the query!
30-Second Interview Answer ⏱️ Recall
"I read execution plans inside-out and bottom-up, following data flow from leaf scan operators to the root. My diagnostic framework focuses on four critical signals: large discrepancies between estimated and actual row counts, heavy operators like table scans on large tables, physical join operator appropriateness (Nested Loop vs Hash vs Merge), and disk spills during sorting or hashing."
Interviewer Follow-Up: What is a Bitmap Index Scan in PostgreSQL? ▼
Answer: When an index seek would require too many random I/Os but a sequential table scan is too slow, PostgreSQL performs a Bitmap Index Scan. It scans the index, builds a bitmask of physical table page numbers containing matching rows, sorts them by physical disk offset, and performs a sequential Bitmap Heap Scan to read pages without random seek thrashing.
🔑 Key Takeaway: Read plans inside-out. The true bottleneck is where Estimated vs Actual rows diverge, causing loop thrashing or disk spills.
Topic 06 • Relational Joins

Join Optimization: Algorithms, Join Ordering & Sizing

■ What is it?
The strategies used by database optimizers to determine the optimal physical join algorithm (Nested Loops, Hash Join, Sort-Merge Join) and the sequence in which multiple tables are combined (Join Ordering).
■ Why does it exist?
Joining 5 tables creates 1,680 possible join order permutations; joining 10 tables creates 17.6 million. Picking the wrong join order or wrong join algorithm can turn a 5ms query into a 5-hour outage.
■ How does it work?
  • Small-Table Joins (Broadcast / Nested Loops): When joining a tiny filtered table (<100 rows) to a large indexed table, Nested Loops executes direct B-Tree seeks in microseconds with zero memory footprint. In distributed systems (Spark/BigQuery), this is executed as a Broadcast Join (copying the tiny table to all worker nodes to avoid network shuffling).
  • Large-Table Joins (Hash Join vs Sort-Merge): For massive unsorted datasets joining on equality (=), the engine hashes the smaller table into memory and probes with the larger table. If datasets are already pre-sorted by index, Sort-Merge Join merges streams linearly with minimal memory overhead.
  • Join Ordering Optimization: Optimizers evaluate Left-Deep, Right-Deep, and Bushy trees using dynamic programming to place the most restrictive filter tables earliest in the pipeline, minimizing intermediate row volume.
■ Visual explanation
Join Algorithm Decision Matrix: ┌─────────────────────┬──────────────────────┬──────────────────────┬──────────────────────┐ │ Join Algorithm │ Time Complexity │ Memory Footprint │ Optimal Use Case │ ├─────────────────────┼──────────────────────┼──────────────────────┼──────────────────────┤ │ Nested Loops │ O(M * log N) │ O(1) Minimal │ Tiny outer + Index │ │ Hash Join │ O(M + N) │ O(M) Hash Table RAM │ Large unsorted equi │ │ Sort-Merge Join │ O(M + N) sorted │ O(1) Pre-sorted │ Pre-sorted or Inequal│ │ Broadcast (Spark) │ O(M + N) 0 Shuffle │ Driver Broadcast RAM │ Dimension < 10-100MB │ └─────────────────────┴──────────────────────┴──────────────────────┴──────────────────────┘
■ Symptoms Massive shuffle network traffic in Spark; query timing out in PostgreSQL during multi-table joins.
■ How to diagnose it Check whether the join table order evaluates high-cardinality tables first, or if a Cartesian product occurred due to missing join predicates.
■ How to fix it Index foreign keys; ensure join predicates are strict equi-joins; broadcast small lookup tables in distributed engines (/*+ BROADCAST(dim) */).
■ Common mistakes Joining large tables on non-indexed text columns; using inequality joins (>=) expecting a Hash Join; joining on disparate data types.
■ Production considerations
In Databricks and Spark SQL, setting spark.sql.autoBroadcastJoinThreshold (default 10MB) properly prevents massive network shuffles on dimensional joins. If tables have data skew, enable Adaptive Query Execution (AQE) skew join optimization.
30-Second Interview Answer ⏱️ Recall
"Join optimization is driven by input cardinality and indexing. Nested Loops dominates small driving tables joining indexed targets; Hash Join dominates large unsorted equi-joins with sufficient memory grants; and Sort-Merge Join excels when inputs are pre-sorted or joining on inequality ranges. In distributed architectures, we broadcast small dimension tables to eliminate shuffle overhead."
Interviewer Follow-Up: What happens if a Hash Join build table exceeds work_mem? ▼
Answer: The engine falls back to a Hybrid / Grace Hash Join. It partitions both relations into matching hash buckets written out to disk (TempDB/workfiles), processing and joining one bucket pair in memory at a time, avoiding OOM crashes at the cost of high disk I/O latency.
🔑 Key Takeaway: Tiny outer + index seek = Nested Loops. Large unsorted = Hash Join. Pre-sorted = Merge Join. Small dimension in distributed SQL = Broadcast.
Topic 07 • Data Access Patterns

Pagination: OFFSET vs Keyset & Cursor Pagination

■ What is it?
The architectural design pattern for retrieving large ordered result sets in manageable chunks (pages) for APIs and user interfaces.
■ Why does it exist?
Fetching 10 million rows in a single query exhausts memory, saturates network bandwidth, and causes high client-side latency.
■ How does it work? (The 3 Pagination Strategies)
  • 1. Offset-Based Pagination (Naive / Problematic): 
    SELECT id, name, created_at FROM orders ORDER BY created_at LIMIT 20 OFFSET 1000000;
    Why OFFSET becomes exponentially expensive: The database does not jump directly to row 1,000,000. It must read and sort all 1,000,020 rows from disk into memory, discard the first 1,000,000 rows, and emit the remaining 20. At Page 50,000, this burns gigabytes of I/O and takes 15+ seconds.
  • 2. Keyset Pagination (Seek Method - Best for Static Sorts): 
    -- Next Page Query (using the last seen created_at & id from previous page):
SELECT id, name, created_at FROM orders 
WHERE (created_at, id) > ('2024-05-01 14:30:00', 45021)
ORDER BY created_at, id LIMIT 20;
    Why Keyset is $O(1)$ constant time: Navigates directly to the exact B-Tree leaf position via index seek, reading exactly 20 rows regardless of whether you are on Page 1 or Page 50,000.
  • 3. Cursor-Based Pagination (Base64 Encoded Token): Encodes the keyset values into an opaque cursor token (e.g. cursor=ZXlKaWRI...). Enables stateless REST APIs to page bidirectionally with consistent $O(1)$ latency.
■ Visual explanation
OFFSET 1,000,000 LIMIT 20: [Read 1..100,000] ──► [Read 100,001..500,000] ──► [Read 500,001..1,000,000] (DISCARD ALL 1,000,000 ROWS!) ──► Emit 20 rows (💥 14.5s) KEYSET PAGINATION: WHERE id > 45021 LIMIT 20 [B-Tree Root] ──► [Branch] ──► Direct Leaf Seek at ID=45021 ──► Emit 20 rows (⚡ 0.8ms)
■ Symptoms Page 1 loads in 5ms; Page 1000 times out after 30 seconds; database CPU spikes during web scraper crawling.
■ How to diagnose it Check slow query logs for OFFSET > 10000 with high disk page buffer reads.
■ How to fix it Refactor endpoint queries from OFFSET to Keyset / Cursor Pagination with an index on (sort_column, tiebreaker_id).
■ Common mistakes Using OFFSET for infinite-scroll mobile feeds; missing tiebreaker unique IDs in keyset queries causing duplicate/skipped rows on identical timestamps.
■ Production considerations
Keyset pagination cannot jump to an arbitrary page (e.g. "Jump to Page 487"). If random-page jumping is strictly mandated by UI, use Deferred Joins with subquery index seeks.
30-Second Interview Answer ⏱️ Recall
"OFFSET pagination degrades linearly to $O(N)$ because the engine must read, sort, and discard all preceding offset rows before returning the target page. In high-scale data engineering, we replace OFFSET with Keyset/Cursor pagination, filtering on indexed column bounds like WHERE (created_at, id) > (:last_date, :last_id). This executes as a direct B-Tree index seek in constant $O(1)$ sub-millisecond time."
Interviewer Follow-Up: What is a Deferred Join and how does it optimize OFFSET pagination? ▼
Answer: If business constraints mandate OFFSET, a Deferred Join uses a covering index subquery to perform the offset on lightweight primary keys only (SELECT id FROM t ORDER BY date LIMIT 20 OFFSET 100000), and then inner joins back to the base table for only those 20 rows, avoiding loading full row payloads during the offset scan.
🔑 Key Takeaway: OFFSET scans and discards preceding rows ($O(N)$); Keyset seeks directly to index markers ($O(1)$).
Topic 08 • Analytical SQL

Window Functions: Mechanics, Performance & Alternatives

■ What is it?
Analytical SQL functions that perform calculations across a partitioned set of rows (window) while preserving individual row identities (unlike GROUP BY which collapses rows).
■ Why does it exist?
Before window functions, ranking, running totals, and period-over-period comparisons required expensive, self-joins or correlated subqueries that scaled quadratically $O(N^2)$.
■ How does it work? (Core Functions & Differences)
  • ROW_NUMBER(): Assigns unique sequential integers (1, 2, 3...) regardless of ties. Ideal for deduplication.
  • RANK(): Assigns identical ranks to ties, skipping subsequent ranks (1, 2, 2, 4...).
  • DENSE_RANK(): Assigns identical ranks to ties without skipping numbers (1, 2, 2, 3...). Ideal for "Top N Salaries".
  • LAG() / LEAD(): Accesses previous or subsequent row values within the partition window without self-joins.
  • SUM() OVER (PARTITION BY ... ORDER BY ...): Computes cumulative running totals. Default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW.
-- Deduplication Pattern:
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY updated_at DESC) AS rn
  FROM user_events
)
SELECT * FROM ranked WHERE rn = 1;
■ Visual explanation
Correlated Subquery / Self-Join (O(N^2) Latency): Outer Row 1 ──► Scans entire table (1M rows) Outer Row 2 ──► Scans entire table (1M rows) ──► 💥 1,000,000,000,000 row evaluations! Window Function with WindowAgg Operator (O(N log N) Latency): Step 1: Partition & Sort input stream by PARTITION BY + ORDER BY keys. Step 2: Stream rows once through a single-pass Window Iterator, tracking running state in RAM.
■ Symptoms Memory spills during WindowAgg operators; queries running slow when sorting large partitions.
■ How to diagnose it Check execution plan for WindowAgg followed by an explicit high-cost Sort operator.
■ How to fix it Create a composite index matching (partition_column, order_column) to deliver pre-sorted streams to WindowAgg with zero sort overhead.
■ Common mistakes Omitting ROWS BETWEEN in running aggregates (default RANGE frame forces duplicate peer sorting in memory).
■ Production considerations
Always specify ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW instead of default RANGE for running totals. ROWS processes one physical tuple at a time in $O(N)$, whereas RANGE must buffer duplicate value peer groups.
30-Second Interview Answer ⏱️ Recall
"Window functions perform analytical calculations across row partitions in a single streaming pass ($O(N \log N)$), replacing $O(N^2)$ correlated self-joins. To optimize window functions, we create composite indexes covering (PARTITION BY, ORDER BY) columns to eliminate explicit sorting and explicitly specify ROWS BETWEEN to avoid duplicate peer buffering."
Interviewer Follow-Up: What is the performance difference between ROWS and RANGE in window frames? ▼
Answer: ROWS calculates window boundaries based on physical offset count, enabling a single-pass accumulator. RANGE calculates boundaries based on logical value equality, forcing the engine to inspect all duplicate peer values in the partition before emitting running totals, adding significant CPU and memory buffer overhead.
🔑 Key Takeaway: Window functions replace O(N²) self-joins with single-pass streams. Index `(partition_col, order_col)` to eliminate sort costs.
Topic 09 • Relational Rewriting

Query Rewriting: CTEs, Subqueries, EXISTS vs IN & Materialized Views

■ What is it?
The disciplined practice of refactoring SQL queries into optimal relational equivalents that enable optimizer pushdowns, avoid redundant materialization, and eliminate unnecessary deduplication.
■ Why does it exist?
Different SQL constructs that produce identical business results can have vastly different execution plan topologies. Understanding engine internals allows engineers to write queries that naturally unlock optimizer optimizations.
■ How does it work? (Core Structural Comparisons)
  • CTEs vs Subqueries vs Temp Tables:
    • Inline CTE / Subquery: Modern optimizers (PostgreSQL 12+, SQL Server, BigQuery) inline and flatten CTEs, pushing predicates down seamlessly.
    • Materialized CTE (WITH x AS MATERIALIZED (...)): Forces the engine to compute and cache the result in memory/temp storage once. Best if referenced 3+ times, but blocks predicate pushdown from outer queries!
    • Temporary Tables: Creates physical temporary tables with their own statistics and indexes. Best for massive multi-step data transformations breaking up complex optimizer search spaces.
  • EXISTS vs IN: EXISTS short-circuits on the first matching row (Semi-Join). IN with subqueries can handle nulls poorly; if the subquery returns a single NULL, NOT IN evaluates to unknown for all rows! Always prefer EXISTS / NOT EXISTS for subquery filtering.
  • UNION vs UNION ALL: UNION executes an expensive physical Distinct Sort / Hash Aggregate across the entire combined dataset to remove duplicates. UNION ALL streams records immediately with zero sorting. Always use UNION ALL unless duplicate elimination is an explicit business requirement.
  • Materialized Views: Physically persists query results on disk and can be refreshed incrementally or on schedule. Excellent for expensive aggregate dashboards.
■ Visual explanation
UNION (Expensive): Stream 1 (10M rows) ──┐ ├──► [Append Operator] ──► [💥 Heavy In-Memory / Disk Deduplication Sort] ──► Output Stream 2 (10M rows) ──┘ UNION ALL (Zero Overhead Streaming): Stream 1 (10M rows) ──┐ ├──► [Append Operator] ──(Direct Stream Out!)──► Output (Instant!) Stream 2 (10M rows) ──┘
■ Symptoms Query hanging inside CTEs; NOT IN returning 0 rows unexpectedly; heavy disk spills on UNION.
■ How to diagnose it Check execution plan for unpushed filters inside CTE boundaries or expensive Distinct / Sort operators below Append nodes.
■ How to fix it Switch UNION to UNION ALL; replace NOT IN with NOT EXISTS; break bloated CTE pipelines into indexed Temp Tables.
■ Common mistakes Defaulting to UNION when streams are mutually exclusive; using NOT IN (SELECT col FROM ...) when col contains NULLs.
■ Production considerations
In PostgreSQL versions prior to 12, CTEs were an absolute optimization fence (materializing unconditionally). In modern engines, use WITH t AS NOT MATERIALIZED (...) if you need to guarantee predicate pushdown.
30-Second Interview Answer ⏱️ Recall
"Query rewriting bridges business logic and execution efficiency. Key rules include: using UNION ALL to avoid duplicate elimination sorts; choosing EXISTS over IN to leverage short-circuiting semi-joins and avoid three-valued null logic traps; and breaking massive monolithic CTE chains into indexed temporary tables to simplify optimizer cardinality estimation on complex joins."
Interviewer Follow-Up: Why does NOT IN return zero rows if the subquery contains a NULL? ▼
Answer: In SQL three-valued logic, x NOT IN (1, 2, NULL) expands to x != 1 AND x != 2 AND x != NULL. Since any comparison with NULL yields UNKNOWN, the entire boolean chain evaluates to UNKNOWN / FALSE, resulting in zero rows returned. NOT EXISTS uses two-valued boolean logic and handles nulls safely.
🔑 Key Takeaway: Default to UNION ALL. Use EXISTS over IN. Break multi-join CTE mega-queries into indexed Temp Tables.
Topic 10 • Physical Storage

Partitioning & Partition Pruning

■ What is it?
The physical division of a giant logical table into smaller, independent physical storage sub-tables based on a partition key (e.g. created_at date ranges or tenant IDs).
■ Why does it exist?
To enable Partition Pruning (skipping 95%+ of physical files/pages during query execution) and facilitate instantaneous bulk data lifecycle management (e.g. DROP PARTITION in milliseconds with zero row-by-row undo/redo logging).
■ How does it work? (The 3 Partitioning Strategies)
  • Range Partitioning: Maps data based on value ranges (e.g. PARTITION BY RANGE (order_date) daily or monthly). Ideal for time-series logs and event telemetry.
  • List Partitioning: Maps data based on explicit discrete values (e.g. PARTITION BY LIST (country_code)). Ideal for multi-region tenancy.
  • Hash Partitioning: Distributes data across $K$ partitions using a cryptographic hash of the key. Eliminates hot spots and balances disk volume evenly.
  • Partition Pruning: During query planning (Static Pruning) or execution (Dynamic Pruning), the optimizer inspects the WHERE clause and skips reading non-qualifying partition sub-tables entirely.
■ Visual explanation
Logical Table: sales (500,000,000 rows across 5 years) Partitioned by Month: [ Jan 2024 (10M) ] [ Feb 2024 (10M) ] [ Mar 2024 (10M) ] ... [ Dec 2024 (10M) ] Query: SELECT * FROM sales WHERE order_date BETWEEN '2024-03-01' AND '2024-03-31'; ──► Static Partition Pruning SKIPS 58 partitions! ──► Reads ONLY the 1 physical partition for March 2024 (98% I/O reduction!)
■ Symptoms Queries on partitioned tables scanning all historical data; dropping old records freezing database due to heavy DELETE transaction logs.
■ How to diagnose it Check execution plan: Look for Partitions Scanned: 1..60 (ALL) instead of Partitions Scanned: 3..3.
■ How to fix it Ensure queries filter directly on the partition key without wrapping it in non-SARGable functions; use ALTER TABLE DROP PARTITION for instantaneous data purging.
■ Common mistakes Over-partitioning (e.g. creating 10,000 hourly partitions causing catalog metadata bloat); partitioning on non-queried columns.
■ Production considerations
In BigQuery and Snowflake, combining Partitioning (by Day/Month) with Clustering (by high-cardinality dimension keys like customer_id) delivers optimal cost reduction and data skipping.
30-Second Interview Answer ⏱️ Recall
"Partitioning physically divides tables into discrete storage segments by range, list, or hash. Its primary performance benefit is Partition Pruning—allowing the optimizer to skip non-qualifying storage partitions entirely during scans. It also simplifies data lifecycle management by enabling instantaneous DDL partition drops instead of high-overhead row-by-row DELETE operations."
Interviewer Follow-Up: What is the difference between Static and Dynamic Partition Pruning? ▼
Answer: Static pruning occurs at compile time when filter literals are constants (e.g. WHERE date = '2024-01-01'). Dynamic Partition Pruning (DPP) occurs at runtime during joins (e.g. joining a date dimension table to a partitioned fact table); the engine broadcasts the filtered date keys to prune fact partitions dynamically during the scan.
🔑 Key Takeaway: Partition pruning skips physical files at the storage layer. Partition by Date/Tenant; drop partitions for instant zero-overhead data purging.
Topic 11 • Concurrency & Integrity

Transactions, Isolation Levels, Locking & MVCC

■ What is it?
The concurrency control and transactional integrity sub-system governing ACID guarantees, lock hierarchies, and Multi-Version Concurrency Control (MVCC).
■ Why does it exist?
To prevent data corruption, dirty reads, non-repeatable reads, and phantom reads when thousands of concurrent transactions read and write shared data pages simultaneously.
■ How does it work?
  • ACID Guarantees:
    • Atomicity: All or nothing (via Write-Ahead Log / WAL).
    • Consistency: Preserves database constraints and schema rules.
    • Isolation: Concurrently executing transactions do not interfere.
    • Durability: Committed changes survive power loss (flushed to WAL).
  • The 4 ANSI Isolation Levels:
    1. Read Uncommitted: Allows Dirty Reads (reading uncommitted data).
    2. Read Committed (Default): Prevents Dirty Reads. Reads only committed snapshots.
    3. Repeatable Read: Prevents Dirty and Non-Repeatable Reads. Guarantees reading the same values if re-queried in the same transaction.
    4. Serializable: Highest isolation. Prevents Phantom Reads via predicate locks or strict two-phase locking (2PL).
  • MVCC (Multi-Version Concurrency Control): Engines (Postgres, Oracle, MySQL InnoDB) never block readers with writers and never block writers with readers. When a row is updated, a new physical tuple version (with transaction visibility IDs xmin/xmax) is written; readers continue reading the previous committed version.
  • Locking & Deadlocks: Locks form a hierarchy (Row $ ightarrow$ Page $ ightarrow$ Table). Shared (S) locks allow concurrent reads; Exclusive (X) locks block all access. A Deadlock occurs when Transaction A holds Lock 1 and waits for Lock 2, while Transaction B holds Lock 2 and waits for Lock 1. The engine's deadlock detector kills the lower-cost transaction.
■ Visual explanation

Writes v2 without blocking reader! Deadlock Cycle: Transaction A [Holds Lock on Table 1] ──(Waits for Lock on Table 2)──► Transaction B ▲ │ └──────────────────(Waits for Lock on Table 1)────────────────────────┘ Engine Deadlock Detector ──► Terminates Transaction B with Error 40P01!
■ Symptoms High lock wait times (LCK_M_X / ExclusiveLock); frequent Deadlock error exceptions in application logs; table bloat.
■ How to diagnose it Inspect sys.dm_tran_locks / pg_stat_activity (checking wait_event_type = 'Lock') and analyze Deadlock Graph XML reports.
■ How to fix it Keep transactions short; acquire locks in identical alphabetical order across all application code paths; enable Read Committed Snapshot Isolation (RCSI).
■ Common mistakes Leaving transactions open during external REST API calls; updating tables in opposite sequences across stored procedures.
■ Production considerations
In PostgreSQL, MVCC generates dead tuples on every UPDATE and DELETE. Autovacuum must be aggressively tuned to reclaim dead tuple storage and prevent table bloat and transaction ID wraparound.
30-Second Interview Answer ⏱️ Recall
"Database concurrency balances isolation levels against lock contention. Modern engines use Multi-Version Concurrency Control (MVCC) so that readers never block writers and writers never block readers by maintaining snapshot tuple versions. We prevent deadlocks by keeping transactions short and enforcing strict, consistent lock acquisition ordering across all application transactions."
Interviewer Follow-Up: What is Lock Escalation in SQL Server? ▼
Answer: When a transaction acquires more than ~5,000 fine-grained row locks on a single table, SQL Server automatically escalates those row locks into a single Exclusive Table Lock to conserve lock manager memory. This blocks all concurrent queries on that table. We prevent escalation by batching large DML operations into smaller chunks (e.g. 2,000 rows per batch).
🔑 Key Takeaway: MVCC enables non-blocking reads via versioned snapshots. Avoid deadlocks by enforcing identical object update ordering.
Topic 12 • Field Troubleshooting

Slow-Query Diagnosis: 20 Production Scenarios

During Lead and Senior Data Engineering interviews, technical interviewers will present ambiguous production degradation symptoms. Master these 20 comprehensive troubleshooting scenarios formatted in the exact Symptom $ ightarrow$ Likely Causes $ ightarrow$ Evidence to Collect $ ightarrow$ Fix $ ightarrow$ Trade-offs framework.

Scenario 01: Table Scan on Column with Existing B-Tree Index▼

■ Symptom: Query runs for 25 seconds executing a Full Table Scan on an 80M row table despite an active B-Tree index on created_at.

■ Likely Causes: Non-SARGable predicate (WHERE CAST(created_at AS DATE) = '2024-05-01') or selectivity exceeding the 3% tipping point.

■ Evidence to Collect: Inspect execution plan filter text for function wrapping; run SELECT COUNT(*) WHERE condition / COUNT(*) to check true selectivity.

■ Fix: Rewrite as half-open range: WHERE created_at >= '2024-05-01' AND created_at < '2024-05-02'.

■ Trade-offs: Code refactor required; zero index storage overhead.

Scenario 02: Sudden Plan Regression after ETL / Parameter Sniffing▼

■ Symptom: Stored procedure normally running in 100ms suddenly takes 35 minutes following server restart.

■ Likely Causes: Parameter Sniffing compiled plan cached on non-representative low-cardinality parameter (Nested Loops plan reused for 10M-row tenant).

■ Evidence to Collect: Compare compiled parameter values vs runtime parameter values in execution plan XML.

■ Fix: Add OPTION (OPTIMIZE FOR UNKNOWN) / OPTION (RECOMPILE) or set plan_cache_mode = force_custom_plan.

■ Trade-offs: Recompile consumes minor CPU per invocation but guarantees plan stability.

Scenario 03: Hash Join TempDB / Disk Memory Spill▼

■ Symptom: Nightly join job slows from 3 mins to 45 mins; storage metrics show heavy TempDB write saturation with yellow warning icon on Hash Join.

■ Likely Causes: Stale statistics caused cardinality underestimation (estimated 100 rows vs actual 5M rows), sizing an undersized memory grant.

■ Evidence to Collect: Check Estimated Rows vs Actual Rows at build node; verify last_analyzed timestamp in catalog.

■ Fix: Run ANALYZE table_name; / UPDATE STATISTICS WITH FULLSCAN; and increase session work_mem.

■ Trade-offs: Stats gathering consumes I/O during maintenance windows.

Scenario 04: Implicit Data Type Conversion destroying Index Seek▼

■ Symptom: Query filtering on indexed VARCHAR column national_id causes 100% CPU spike and table scan.

■ Likely Causes: Application ORM passed integer literal (WHERE national_id = 12345678), triggering implicit CONVERT_IMPLICIT cast on all rows.

■ Evidence to Collect: Look for CONVERT_IMPLICIT in plan predicate filter.

■ Fix: Pass string literal: WHERE national_id = '12345678'.

■ Trade-offs: Zero database side-effects; immediate sub-millisecond fix.

Scenario 05: Correlated Subquery CPU Thrashing (RBAR Execution)▼

■ Symptom: Dashboard query containing scalar subquery in SELECT projection runs for 12 minutes.

■ Likely Causes: Correlated subquery executing row-by-agonizing-row (RBAR) 5 million times in a nested loop.

■ Evidence to Collect: Check execution plan for subquery loops count matching outer table row count.

■ Fix: Decorrelate into set-based LEFT JOIN or pre-aggregated CTE.

■ Trade-offs: Single-pass hash join executes in 1.5 seconds.

Scenario 06: Exponential Degradation in Deep OFFSET Pagination▼

■ Symptom: Page 1 of search API returns in 10ms; Page 500 times out after 30 seconds.

■ Likely Causes: OFFSET 50000 LIMIT 20 forces the engine to read and sort 50,020 rows from disk before discarding the first 50,000.

■ Evidence to Collect: Query text inspection showing high OFFSET values; execution plan showing full index scan.

■ Fix: Implement Keyset Pagination: WHERE (created_at, id) > (:last_date, :last_id) ORDER BY created_at, id LIMIT 20.

■ Trade-offs: Keyset cannot jump to arbitrary random page numbers.

Scenario 07: Massive Key Lookups / Bookmark Lookups on Secondary Index▼

■ Symptom: Query uses Index Seek on orders(customer_id) but takes 8 seconds with heavy random I/O.

■ Likely Causes: Missing covering columns forces the engine to execute 200,000 individual random Bookmark Lookups into the clustered heap.

■ Evidence to Collect: Plan shows Key Lookup (Clustered) with 90%+ attributed cost.

■ Fix: Convert to Covering Index: CREATE INDEX idx_cov ON orders(customer_id) INCLUDE (order_total, order_date);.

■ Trade-offs: Slightly increases index storage space on disk.

Scenario 08: Missing Leading Column on Composite Index▼

■ Symptom: Composite index exists on (tenant_id, status, created_at), but query on WHERE status = 'ACTIVE' scans the entire table.

■ Likely Causes: B-Tree is ordered primarily by tenant_id. Filtering without the leading column prevents B-Tree seek navigation.

■ Evidence to Collect: Check index definition order vs query WHERE predicates.

■ Fix: Include tenant_id in the filter or create a secondary index with status as the leading key.

■ Trade-offs: Extra index consumes write overhead during inserts.

Scenario 09: UNION vs UNION ALL Accidental Deduplication Sort▼

■ Symptom: Aggregating two 10M row telemetry tables takes 45 seconds with heavy CPU and TempDB spill.

■ Likely Causes: Using UNION instead of UNION ALL forces an unnecessary in-memory distinct sort across 20 million records.

■ Evidence to Collect: Execution plan shows Distinct / Aggregate Sort operator consuming 85% of query cost.

■ Fix: Replace UNION with UNION ALL.

■ Trade-offs: Streams instantly in 0.5s with zero memory allocation.

Scenario 10: NOT IN Returning Zero Rows Due to NULLs▼

■ Symptom: SELECT * FROM customers WHERE id NOT IN (SELECT customer_id FROM blacklist) returns 0 rows, even though blacklist has only 5 rows.

■ Likely Causes: blacklist.customer_id contains a single NULL, causing three-valued logic to evaluate to UNKNOWN for all rows.

■ Evidence to Collect: Run SELECT COUNT(*) FROM blacklist WHERE customer_id IS NULL;.

■ Fix: Rewrite using NOT EXISTS (SELECT 1 FROM blacklist b WHERE b.customer_id = customers.id).

■ Trade-offs: Handles NULLs safely and enables Anti-Semi-Join plan optimization.

Scenario 11: Table Bloat & Dead Tuples in PostgreSQL▼

■ Symptom: A 500MB PostgreSQL table occupies 45GB on disk; sequential scans take 40 seconds.

■ Likely Causes: MVCC dead tuple accumulation from heavy update workloads combined with lagging/misconfigured Autovacuum.

■ Evidence to Collect: Check n_dead_tup in pg_stat_user_tables and run pgstattuple.

■ Fix: Run pg_repack or VACUUM FULL during maintenance window, and tune autovacuum_vacuum_scale_factor = 0.05.

■ Trade-offs: VACUUM FULL acquires an exclusive table lock; pg_repack reclaims space online.

Scenario 12: High CXPACKET / Parallelism Skew Bottleneck▼

■ Symptom: Query uses 16 CPU cores but takes longer than running on 1 core; top wait statistic is CXPACKET / CXCONSUMER.

■ Likely Causes: Severe data skew across parallel exchange thread buffers; 15 threads finish in 100ms and wait idle while 1 thread processes 95% of skewed data.

■ Evidence to Collect: Inspect actual row counts per thread in execution plan properties.

■ Fix: Tune Cost Threshold for Parallelism (raise from default 5 to 50); resolve underlying data skew.

■ Trade-offs: Optimizes multi-core throughput across concurrent sessions.

Scenario 13: High Lock Contention & Lock Escalation▼

■ Symptom: Running an UPDATE statement on 20,000 rows freezes all concurrent web application read queries.

■ Likely Causes: Lock Escalation: acquiring >5,000 row locks caused SQL Server to escalate to an Exclusive Table Lock (X).

■ Evidence to Collect: Check sys.dm_tran_locks for request_mode = 'X' and resource_type = 'OBJECT'.

■ Fix: Chunk batch updates into transactions of 2,000 rows using WHILE loop with TOP (2000).

■ Trade-offs: Prevents table-level lock blocking while processing batch.

Scenario 14: Deadlock Cycle on Concurrent Inserts/Updates▼

■ Symptom: Application logs show intermittent Deadlock victim error code 40P01 / 1205.

■ Likely Causes: Two transactions update Table A and Table B in reverse order (Tx1: A then B; Tx2: B then A).

■ Evidence to Collect: Capture Deadlock XML graph in Extended Events.

■ Fix: Enforce strict, alphabetical resource acquisition ordering across all application codebases.

■ Trade-offs: Eliminates circular lock wait dependencies.

Scenario 15: Non-Deterministic UDF Blocking Predicate Pushdown▼

■ Symptom: Query joining view to partitioned fact table scans 5 years of partitions instead of 1 day.

■ Likely Causes: The view contains a scalar UDF not marked as DETERMINISTIC / IMMUTABLE, preventing optimizer from pushing filters below the join.

■ Evidence to Collect: Plan shows Filter operator situated above Join operator rather than at leaf scan.

■ Fix: Mark UDF as IMMUTABLE / inline the expression inside view definition.

■ Trade-offs: Unlocks partition pruning and predicate pushdown.

Scenario 16: Out-of-Memory Multi-Column Sort on LOB Payloads▼

■ Symptom: Query extracting logs crashes with OOM error or freezes TempDB.

■ Likely Causes: SELECT * ... ORDER BY user_id, event_time, payload pulls massive JSON/Text payload strings into sort memory buffers.

■ Evidence to Collect: High average row width in plan; memory grant exceeding quota.

■ Fix: Enforce Projection Pushdown (select only required keys); index (user_id, event_time) to provide natural pre-sorted stream.

■ Trade-offs: Eliminates physical sort operator entirely.

Scenario 17: Spark Data Skew Shuffle Stage Stragglers▼

■ Symptom: Spark SQL job reaches 199/200 tasks in 30 seconds; task 200 hangs for 45 minutes.

■ Likely Causes: Data Skew on join key (e.g. customer_id = NULL or tenant 0 has 50M records routed to single partition).

■ Evidence to Collect: Spark UI stage details: Task 200 shuffle read size = 45GB while other tasks = 10MB.

■ Fix: Enable Spark AQE: spark.sql.adaptive.skewJoin.enabled = true or salting the skewed join key.

■ Trade-offs: Spreads skewed key across multiple worker partitions evenly.

Scenario 18: BigQuery Slot Contention & High Bytes Billed▼

■ Symptom: BigQuery analytical query costs $45 per run and experiences slot wait throttling.

■ Likely Causes: SELECT * on unpartitioned, unclustered table scanning 9TB of raw parquet storage.

■ Evidence to Collect: BigQuery execution graph: Bytes scanned vs bytes returned ratio.

■ Fix: Partition by date, cluster by high-cardinality dimension keys, and select only referenced columns.

■ Trade-offs: Reduces bytes scanned from 9TB to 120MB (98% cost reduction).

Scenario 19: Correlated Columns Independence Assumption Failure▼

■ Symptom: Query filtering on WHERE make = 'Ford' AND model = 'F-150' estimates 1 row, causing wrong join selection.

■ Likely Causes: Independence assumption multiplied selectivities ($0.05 imes 0.02 = 0.001$), underestimating 500,000 actual matching records.

■ Evidence to Collect: Plan shows Estimated Rows: 1, Actual Rows: 500,000.

■ Fix: Create multi-column extended statistics on (make, model).

■ Trade-offs: Eliminates cardinality underestimation and memory spills.

Scenario 20: Clustered Index Random Page Split I/O Thrashing▼

■ Symptom: High write latency and storage fragmentation during batch inserts into table with UUID primary key.

■ Likely Causes: Clustered index on random UUID (v4) forces continuous random 50/50 B-Tree page splits and I/O write amplification.

■ Evidence to Collect: Check Page Splits/sec performance counter and index fragmentation percentage (>80%).

■ Fix: Change clustered index to sequential BIGINT IDENTITY or sequential UUIDs (UUIDv7 / NEWSEQUENTIALID()).

■ Trade-offs: Inserts append contiguously at the end of the B-Tree with zero mid-leaf page splits.

Framework 1: Conceptual Questions (Definition → Mechanism → Example) ⏱️ 45 Seconds

"I implement Keyset/Cursor Pagination rather than OFFSET (What).   • ❌ WHERE email LIKE '%@gmail.com' $ ightarrow$ ✅ Full-text / Reverse index
🎯 Join Decision Matrix
  • Nested Loops: Outer table < 100 rows + Inner table indexed. $O(M \log N)$.
  • Hash Join: Large unsorted datasets + Equi-join (=) + Adequate RAM. $O(M+N)$.
  • Sort-Merge Join: Pre-sorted streams or inequality joins (<, >=). $O(M+N)$.
  • Broadcast (Spark): Small lookup table < 10MB broadcast to workers (0 shuffle).
🔍 Execution Plan Red Flags
  • Est vs Actual Rows: $>10 imes$ divergence = Stale stats or correlated columns.
  • Yellow Warning Icons: Disk spills (Hash/Sort) or Type Conversion warnings.
  • Filter above Join: Predicate pushdown blocked by non-deterministic UDF.
  • Nested Loop with millions of rows: Cardinality underestimation crash.

30-Minute Interview Revision Sheet

■ 10 Critical Principles to Re-read Before the Interview:
  1. Declarative vs Imperative: SQL specifies the target relational set. The engine parses (AST), binds (Catalog), optimizes (RBO rewrites + CBO costing), and executes (Volcano iterators) against the RAM buffer pool.
  2. B-Tree Fanout & Depth: Keep index keys narrow. A 4-level B-Tree can index 100 million rows with only 4 page reads.
  3. Covering Index with INCLUDE: Stores payload columns at leaf level without bloating branch nodes, turning Key Lookups into $O(1)$ Index-Only Scans.
  4. The Tipping Point (1-5%): An unclustered index seek becomes more expensive than a sequential table scan when matching rows exceed 3-5% due to random I/O bookmark lookups.
  5. SARGability Formula: Always isolate raw indexed columns: col OPERATOR literal_constant. Never wrap indexed columns in functions or implicit type casts.
  6. Cardinality Error Cascade: Independence assumption failures on correlated columns cause $10 imes ightarrow 100 imes ightarrow 10,000 imes$ row underestimation, triggering disastrous Nested Loops and memory spills.
  7. Join Selection: Tiny outer + Index = Nested Loops. Large unsorted equi-join = Hash Join. Pre-sorted = Merge Join.
  8. Pagination: Replace $O(N)$ OFFSET with $O(1)$ Keyset pagination using tuple markers: WHERE (date, id) > (:last_date, :last_id).
  9. Query Rewriting: Default to UNION ALL (zero sort). Use EXISTS over IN (safe null logic + semi-join). Break giant CTEs into indexed Temp Tables.
  10. MVCC & Concurrency: Readers never block writers and writers never block readers. Avoid deadlocks by enforcing identical lock acquisition order.

Q1: Why do databases not execute SQL statements directly? ▼

Senior Answer: SQL is declarative—it defines the required relational dataset without specifying physical retrieval algorithms. The database must compile SQL into an Abstract Syntax Tree (AST), validate semantics against the data catalog, evaluate physical operator combinations using a Cost-Based Optimizer, and execute an imperative iterator tree against the memory buffer pool.

\n
Q2: What is the exact distinction between syntactic and semantic query validation? ▼

Senior Answer: Syntactic validation checks SQL grammar, keywords, and punctuation to construct an Abstract Syntax Tree with zero catalog access. Semantic validation (binding) queries the system catalog to verify table/column existence, resolve data types, and check user authorization.

\n
Q3: What is the Volcano Iterator Model? ▼

Senior Answer: A demand-driven execution model where every physical operator in the plan tree implements open(), next(), and close(). The root operator pulls tuples one-by-one from child operators, minimizing intermediate memory materialization.

\n
Q4: How does the Buffer Pool Manager optimize disk I/O? ▼

Senior Answer: It maintains an in-memory cache of 8KB database pages using LRU/Clock eviction algorithms. If a requested page resides in RAM (Cache Hit), it returns in nanoseconds; if missing (Cache Miss), it initiates asynchronous storage I/O.

\n
Q5: What is the difference between compile time and run time in database engines? ▼

Senior Answer: Compile time is CPU-bound in-memory compilation (lexing, parsing, binding, and cost optimization). Run time encompasses storage I/O, memory grant buffer allocations, lock acquisitions, CPU tuple evaluations, and network serialization.

\n
Q6: Why are prepared statements recommended for high-throughput OLTP systems? ▼

Senior Answer: Prepared statements parse, bind, and optimize the SQL string once, caching the compiled execution plan. Subsequent executions pass parameters directly, bypassing compilation CPU latency.

\n
Q7: What is the search space of a query optimizer? ▼

Senior Answer: The set of all mathematically equivalent physical execution trees for a given logical query, comprising join order permutations, access paths (seek vs scan), join algorithms, and aggregation strategies.

\n
Q8: Why is exhaustive optimizer search impossible for queries with 15+ joins? ▼

Senior Answer: Join order permutations scale factorially O(N!). For 15 tables, there are billions of permutations, so optimizers use dynamic programming memoization and search time budgets to find a good-enough plan within milliseconds.

\n
Q9: What is the role of the System Catalog (Data Dictionary)? ▼

Senior Answer: It stores schema metadata: table definitions, column types, constraints, index structures, user permissions, and statistical histograms.

\n
Q10: What happens when DDL modifies a table with cached prepared statements? ▼

Senior Answer: The database increments the table's schema version. When a cached plan detects a stale schema version, it invalidates the plan and triggers an automatic re-parse and re-compile.

\n
Q11: What is constant folding in query optimization? ▼

Senior Answer: A rule-based rewrite that precomputes static, deterministic expressions (e.g., DATEADD(day, -7, '2024-01-08') -> '2024-01-01') at compile time.

\n
Q12: What is projection pushdown (column pruning)? ▼

Senior Answer: A rule-based optimization that eliminates unreferenced columns at the storage scan layer, minimizing memory buffer consumption and disk I/O bandwidth.

\n
Q13: What is predicate pushdown? ▼

Senior Answer: Moving WHERE filter conditions down the relational tree as close as possible to the physical storage scan to eliminate rows before expensive joins or aggregations.

\n
Q14: Why is rule-based optimization alone insufficient for modern databases? ▼

Senior Answer: RBO applies static rules blindly without knowing data volume, data distribution, indexing, or memory grants. It cannot decide whether a 10-row lookup needs an index or a 100M-row scan needs sequential I/O.

\n
Q15: What are the core components of a database cost model? ▼

Senior Answer: Sequential I/O page reads (cost=1.0), Random I/O seeks (cost=1.1-4.0), CPU tuple evaluations (cost=0.01), CPU operator/hash costs (cost=0.0025), and disk spill penalties.

\n
Q16: What is the structural difference between a Clustered and Non-Clustered index? ▼

Senior Answer: A clustered index physically sorts table rows on disk at the B-Tree leaf level (1 per table). A non-clustered index stores sorted key columns and bookmark row pointers back to the base table heap or clustered key.

\n
Q17: Why do databases use B+ Trees instead of standard Binary Search Trees? ▼

Senior Answer: B+ Trees have high fanout (hundreds of keys per 8KB page), keeping tree depth low (3-4 levels for 100M rows) to minimize disk page reads. Doubly linked leaf nodes allow lightning-fast sequential range scans.

\n
Q18: What is a Covering Index? ▼

Senior Answer: A non-clustered index that includes all columns referenced in the query's SELECT, WHERE, and JOIN clauses, enabling an Index-Only Scan with zero random bookmark lookups into the heap.

\n
Q19: What is the purpose of the INCLUDE clause in index creation? ▼

Senior Answer: It stores payload columns strictly at the leaf level without adding them to intermediate B-Tree branch nodes, preserving high fanout and shallow tree depth while achieving index coverage.

\n
Q20: What is the Equality-Sort-Range (ESR) rule for composite indexes? ▼

Senior Answer: Order composite index keys as: Equality columns first, then Sort/Range columns second, then INCLUDE payload columns third.

\n
Q21: What is the Index Tipping Point? ▼

Senior Answer: The selectivity threshold (typically 1% to 5% of total table rows) where the random I/O overhead of secondary index seeks plus bookmark lookups becomes more expensive than a sequential full table scan.

\n
Q22: What is an Index-Only Scan? ▼

Senior Answer: An execution operator where all requested columns are satisfied directly from index leaf pages without touching the underlying table heap pages.

\n
Q23: What causes B-Tree page splits and how do they impact performance? ▼

Senior Answer: Inserting rows out of order into a full 8KB leaf page forces the engine to split the page 50/50, causing I/O write amplification, index fragmentation, and empty page space.

\n
Q24: Why should clustered index keys be monotonically increasing? ▼

Senior Answer: Monotonically increasing keys (e.g. BIGINT IDENTITY or UUIDv7) append new rows contiguously to the end of the B-Tree leaf level, eliminating random mid-leaf page splits.

\n
Q25: Why is indexing a low-cardinality boolean column usually useless? ▼

Senior Answer: A 50/50 boolean column has a selectivity of 0.5 (50%), far exceeding the 3% tipping point; the optimizer will always prefer a sequential table scan unless data is heavily skewed and filtered via a partial index.

\n
Q26: What is a Filtered / Partial Index? ▼

Senior Answer: An index created with a WHERE clause (e.g. CREATE INDEX idx ON orders(date) WHERE status = 'UNPAID') that indexes only the rare rows satisfying the filter, saving 95%+ disk space.

\n
Q27: What is the difference between an Index Seek and an Index Scan? ▼

Senior Answer: An Index Seek traverses the B-Tree from root to leaf in O(log N) to find specific keys. An Index Scan reads all leaf pages sequentially in O(N) order.

\n
Q28: What is a Bitmap Index Scan in PostgreSQL? ▼

Senior Answer: An access path that reads index pages, builds an in-memory bitmap of physical table page numbers containing matches, sorts them by physical disk offset, and reads heap pages in sequential I/O order.

\n
Q29: How does index fill factor impact write performance? ▼

Senior Answer: Setting a lower fill factor (e.g. 80-90%) leaves free space on leaf pages during index rebuilds, absorbing future updates and inserts without triggering immediate page splits.

\n
Q30: What is a Function-Based / Expression Index? ▼

Senior Answer: An index built on the output of a deterministic function (e.g., CREATE INDEX idx ON users (LOWER(email))), allowing B-Tree seeks on queries filtering by that expression.

\n
Q31: Why does a composite index on (A, B) not support queries filtering only on B? ▼

Senior Answer: The composite B-Tree is sorted primarily by column A. Without knowing A, the engine cannot perform a binary search root-to-leaf on B, forcing a full index scan.

\n
Q32: What is an Index Skip Scan? ▼

Senior Answer: An optimization where the engine iterates distinct values of the leading composite key A and executes mini-seeks on B for each distinct A value.

\n
Q33: What is the difference between a Unique Index and a Primary Key? ▼

Senior Answer: A primary key is an entity integrity constraint that enforces uniqueness and disallows NULLs (often default clustered). A unique index is a physical structure that enforces uniqueness and can allow one NULL.

\n
Q34: How do unindexed Foreign Keys impact parent table DELETE operations? ▼

Senior Answer: Deleting a row from a parent table requires checking child tables for referencing records. Without an index on the child's foreign key, the engine must execute a full table scan on the child table.

\n
Q35: What is index fragmentation and how do you resolve it? ▼

Senior Answer: Logical fragmentation occurs when B-Tree leaf pages are out of physical storage order due to page splits. Resolve by running ALTER INDEX ... REBUILD (or REORGANIZE).

\n
Q36: What does SARGable mean? ▼

Senior Answer: Search-Argument-Able: a query predicate written such that the optimizer can use a B-Tree index seek rather than scanning the entire table.

\n
Q37: Why is WHERE YEAR(created_at) = 2024 non-SARGable? ▼

Senior Answer: The B-Tree stores raw timestamp values. Wrapping the column in the YEAR() function forces the engine to evaluate the function for every single row in the table.

\n
Q38: How do you rewrite WHERE YEAR(created_at) = 2024 into a SARGable format? ▼

Senior Answer: WHERE created_at >= '2024-01-01 00:00:00' AND created_at < '2025-01-01 00:00:00'.

\n
Q39: Why does WHERE column LIKE '%term' disable index seeks? ▼

Senior Answer: B-Trees are sorted lexicographically left-to-right. A leading wildcard means the starting prefix is unknown, making root-to-leaf binary search impossible.

\n
Q40: How do you optimize suffix searches like LIKE '%@gmail.com'? ▼

Senior Answer: Store a reverse column (e.g. reverse_email) indexed with a trailing wildcard (WHERE reverse_email LIKE 'moc.liamg@%'), or use Trigram / Full-Text indexing.

\n
Q41: Why does implicit type conversion break SARGability? ▼

Senior Answer: Data type precedence rules force the engine to wrap the lower-precedence column in an internal CAST() function on every row, destroying B-Tree seekability.

\n
Q42: How do you fix implicit type conversions in queries? ▼

Senior Answer: Match literal parameter data types strictly to column definitions (e.g., pass '12345' as a string literal when querying a VARCHAR column).

\n
Q43: Why is WHERE price * 0.9 > 100 non-SARGable? ▼

Senior Answer: Arithmetic on the column modifies the indexed value. Rewrite by isolating the column: WHERE price > (100 / 0.9).

\n
Q44: Is WHERE col IS NULL SARGable in modern databases? ▼

Senior Answer: Yes, in PostgreSQL and SQL Server B-Trees index NULL values, allowing direct index seeks for IS NULL if selectivity is high.

\n
Q45: Why is WHERE col1 = 'A' OR col2 = 'B' often slow, and how do you fix it? ▼

Senior Answer: An OR across disparate unindexed columns prevents single index seeks. Fix by splitting into a UNION ALL of two index-seeking queries: (SELECT ... WHERE col1='A') UNION ALL (SELECT ... WHERE col2='B' AND col1 != 'A').

\n
Q46: What is Cardinality in database query planning? ▼

Senior Answer: The estimated count of rows produced by a relational operator. It is the primary input dictating join algorithms, join orders, and memory grant allocations.

\n
Q47: What is an Equi-Height (Equal-Depth) Histogram? ▼

Senior Answer: A statistical histogram where column values are partitioned into buckets such that each bucket contains an equal quantity of rows, accurately capturing data skew.

\n
Q48: What is the Number of Distinct Values (NDV) and Density? ▼

Senior Answer: NDV is the count of unique column values. Density is defined as 1 / NDV; the optimizer uses density to estimate equality filter selectivity when histograms are absent.

\n
Q49: What causes the Cardinality Estimation Error Cascade? ▼

Senior Answer: An error in row estimation at a leaf filter operator multiplies exponentially up the plan tree, causing wrong join selections (Nested Loops instead of Hash) and undersized memory grants.

\n
Q50: What is the Predicate Independence Assumption? ▼

Senior Answer: The optimizer assumes conditions on different columns are statistically independent (P(A and B) = P(A) * P(B)). It fails on correlated attributes (e.g. City='SF' and State='CA').

\n
Q51: How do you fix correlated predicate cardinality underestimation? ▼

Senior Answer: Create Extended / Multi-Column Statistics (e.g. CREATE STATISTICS s ON col1, col2 FROM table) and run ANALYZE.

\n
Q52: What is Parameter Sniffing? ▼

Senior Answer: When a database compiles and caches an execution plan optimized for the specific parameter passed during first execution. If subsequent parameters have skewed data volumes, the cached plan degrades.

\n
Q53: How do you diagnose stale statistics? ▼

Senior Answer: Compare Estimated Rows vs Actual Rows in EXPLAIN ANALYZE. A discrepancy greater than 10x indicates stale or missing statistics.

\n
Q54: How do you fix parameter sniffing in SQL Server? ▼

Senior Answer: Add OPTION (OPTIMIZE FOR UNKNOWN), use OPTION (RECOMPILE), or split stored procedure logic based on tenant cardinality.

\n
Q55: What triggers automatic statistics updates? ▼

Senior Answer: When row modifications (inserts, updates, deletes) exceed a threshold percentage (typically 10-20%) since the last analyze run.

\n
Q56: What is the difference between EXPLAIN and EXPLAIN ANALYZE? ▼

Senior Answer: EXPLAIN shows compile-time estimated costs and row counts without running the query. EXPLAIN ANALYZE actually executes the query, returning true runtime duration, memory grants, and buffer hits.

\n
Q57: In what order should you read an execution plan? ▼

Senior Answer: Read inside-out and bottom-up, starting from the most deeply indented leaf scan operators up to the root.

\n
Q58: What is a Nested Loops Join and when is it optimal? ▼

Senior Answer: An operator that iterates outer rows and performs an inner index seek for each row. Optimal when the outer driving set is tiny (<100 rows) and the inner table is indexed.

\n
Q59: What is a Hash Join and when is it optimal? ▼

Senior Answer: An operator that builds an in-memory hash table on the smaller relation and probes it with the larger relation. Optimal for large unsorted datasets joining on equality (=).

\n
Q60: What is a Sort-Merge Join and when is it optimal? ▼

Senior Answer: An operator that advances cursors along two pre-sorted streams in lockstep. Optimal when datasets are already sorted on join keys or joining on inequality ranges (<, >=).

\n
Q61: What causes a Hash Join to spill to disk? ▼

Senior Answer: When the build-side relation exceeds the allocated work memory grant, forcing the engine to partition and spill hash buckets to TempDB/workfiles.

\n
Q62: What is a Key Lookup / Bookmark Lookup? ▼

Senior Answer: When a non-clustered index seek matches rows but must fetch unindexed columns by chasing row pointers into the clustered table heap.

\n
Q63: What is a Stream Aggregate vs Hash Aggregate? ▼

Senior Answer: Stream Aggregate computes groupings on pre-sorted input with O(1) memory. Hash Aggregate builds an in-memory hash table of groups for unsorted data.

\n
Q64: What is a Top-N Sort? ▼

Senior Answer: An optimized sort operator for ORDER BY ... LIMIT K queries that maintains an in-memory priority queue of size K in O(N log K) time without sorting the entire dataset.

\n
Q65: What is the cost metric in PostgreSQL explain plans? ▼

Senior Answer: A dimensionless estimate of work: (Page_Reads * page_cost) + (Tuples * cpu_cost).

\n
Q66: What does 'Sort Method: external merge Disk' mean? ▼

Senior Answer: The dataset being sorted exceeded available work_mem / memory grants and was partitioned into temporary disk runs.

\n
Q67: What is an Adaptive Join in modern engines? ▼

Senior Answer: A runtime optimization where the engine defers deciding between Nested Loops and Hash Join until runtime based on actual row counts materialized at stage boundaries.

\n
Q68: What is a Semi-Join vs Anti-Semi-Join? ▼

Senior Answer: A Semi-Join returns outer rows that match at least one inner row (EXISTS). An Anti-Semi-Join returns outer rows that have zero matches (NOT EXISTS).

\n
Q69: What does a Filter operator situated ABOVE a Join operator signify? ▼

Senior Answer: Predicate pushdown failure—the engine joined all rows before filtering, indicating non-deterministic UDFs or non-inlined views.

\n
Q70: What is the CXPACKET wait type in SQL Server? ▼

Senior Answer: A parallelism exchange wait occurring when worker threads finish early and wait for straggler threads to complete skewed data chunks.

\n
Q71: Why does OFFSET pagination degrade linearly O(N)? ▼

Senior Answer: The database must read, sort, and discard all preceding offset rows before returning the target page.

\n
Q72: How does Keyset Pagination achieve O(1) constant time? ▼

Senior Answer: It navigates directly to the B-Tree leaf position using indexed column filters: WHERE (date, id) > (:last_date, :last_id) LIMIT 20.

\n
Q73: Why should you prefer UNION ALL over UNION? ▼

Senior Answer: UNION executes an expensive in-memory/disk distinct sort to remove duplicates; UNION ALL streams records immediately with zero sorting.

\n
Q74: Why is NOT EXISTS preferred over NOT IN for subqueries? ▼

Senior Answer: NOT IN evaluates to UNKNOWN/false for all rows if the subquery returns a single NULL value; NOT EXISTS handles NULLs safely and enables Anti-Semi-Joins.

\n
Q75: What is the performance difference between CTEs and Temporary Tables? ▼

Senior Answer: Inline CTEs are flattened by the optimizer for pushdown; Temporary Tables persist physical storage with their own statistics and indexes, ideal for breaking up massive multi-join queries.

\n
Q76: What is a Broadcast Hash Join in Spark/Databricks? ▼

Senior Answer: Copying a small lookup table (<10MB) to all executor nodes, eliminating expensive network shuffling of the large fact table.

\n
Q77: What is Data Skew in distributed joins and how do you fix it? ▼

Senior Answer: When uneven key distribution causes one executor task to process 90% of data. Fix via Spark AQE skew join or key salting.

\n
Q78: What is the difference between ROW_NUMBER(), RANK(), and DENSE_RANK()? ▼

Senior Answer: ROW_NUMBER assigns strictly sequential integers (1,2,3); RANK assigns identical ranks with gaps for ties (1,2,2,4); DENSE_RANK assigns identical ranks without gaps (1,2,2,3).

\n
Q79: Why should you specify ROWS BETWEEN in window running totals? ▼

Senior Answer: Default RANGE frame buffers all duplicate peer rows in memory; ROWS processes one physical tuple at a time in a single-pass streaming accumulator.

\n
Q80: How do window functions outperform correlated subqueries? ▼

Senior Answer: Window functions sort and stream partitions in a single pass O(N log N), replacing O(N^2) quadratic nested loop subqueries.

\n
Q81: What is Partition Pruning? ▼

Senior Answer: The storage engine skips reading non-qualifying partition sub-tables entirely based on WHERE criteria on the partition key.

\n
Q82: What is a Deferred Join in pagination? ▼

Senior Answer: Using a covering index subquery to perform OFFSET on lightweight IDs only, then inner joining back to the base table for the 20 target rows.

\n
Q83: What is Subquery Decorrelation? ▼

Senior Answer: An optimizer transformation that converts correlated subqueries into set-based joins, enabling Hash and Merge joins.

\n
Q84: What is a Materialized View and when should you use it? ▼

Senior Answer: A precomputed, physically stored query result table on disk, refreshed periodically. Ideal for expensive analytical aggregates.

\n
Q85: What is the impact of DISTINCT on query performance? ▼

Senior Answer: DISTINCT forces a full dataset sort or hash aggregate to eliminate duplicates; remove it if data is already unique by schema constraints.

\n
Q86: What is Multi-Version Concurrency Control (MVCC)? ▼

Senior Answer: A concurrency mechanism where readers never block writers and writers never block readers by maintaining snapshot tuple versions.

\n
Q87: What is the difference between Read Committed and Repeatable Read isolation? ▼

Senior Answer: Read Committed takes a new snapshot per statement (preventing dirty reads); Repeatable Read holds a single snapshot for the entire transaction (preventing non-repeatable reads).

\n
Q88: What is a Phantom Read? ▼

Senior Answer: When a transaction re-executes a range query and discovers new 'phantom' rows inserted and committed by another concurrent transaction.

\n
Q89: What is a Deadlock and how does the database resolve it? ▼

Senior Answer: A circular dependency where Tx1 holds Lock A and waits for Lock B, while Tx2 holds Lock B and waits for Lock A. The deadlock detector terminates the lower-cost transaction.

\n
Q90: How do you prevent deadlocks in application code? ▼

Senior Answer: Acquire locks in identical alphabetical order across all application transactions and keep transactions as short as possible.

\n
Q91: What is Lock Escalation in SQL Server? ▼

Senior Answer: Automatically converting >5,000 fine-grained row locks into an Exclusive Table Lock to save lock memory, blocking concurrent queries.

\n
Q92: How do you avoid lock escalation during large batch updates? ▼

Senior Answer: Process updates in small batches (e.g. 2,000 rows per loop transaction).

\n
Q93: What is table bloat in PostgreSQL MVCC? ▼

Senior Answer: Dead tuple versions accumulating on disk from heavy updates/deletes that have not been reclaimed by Autovacuum.

\n
Q94: What is the Write-Ahead Log (WAL)? ▼

Senior Answer: An append-only transaction log on disk where changes are flushed before data pages are written, guaranteeing Durability (ACID).

\n
Q95: What is Read Committed Snapshot Isolation (RCSI) in SQL Server? ▼

Senior Answer: Enabling MVCC row versioning in TempDB for Read Committed, eliminating shared read locks and preventing readers from blocking writers.

\n
Q96: What is an Intent Lock (e.g. IX, IS)? ▼

Senior Answer: A hierarchical lock placed on higher levels (Table/Page) indicating that a transaction holds fine-grained locks on lower-level rows, preventing full table lock conflicts.

\n
Q97: Why should you never execute external REST API calls inside an open SQL transaction? ▼

Senior Answer: Network latency or timeouts keep database row/table locks open for seconds, causing massive connection pool exhaustion and lock queues.

\n
Q98: What is Adaptive Query Execution (AQE) in Spark 3+? ▼

Senior Answer: Dynamic runtime optimization at stage boundaries: dynamically converting Sort-Merge to Broadcast Joins, coalescing shuffle partitions, and handling data skew.

\n
Q99: How does BigQuery optimize queries under the hood? ▼

Senior Answer: Columnar Capacitor storage format, dynamic slot allocation, and automatic partition/cluster block skipping.

\n
Q100: What is the #1 golden rule of a Senior Database Performance Engineer? ▼

Senior Answer: Never guess. Profile the execution plan, compare Estimated vs Actual rows, isolate the dominant resource cost (I/O vs CPU vs Memory), and verify with benchmarks.

Index Seek
An access path that navigates a B-Tree index from root to leaf in O(log N) time to pinpoint specific matching key ranges.
\n
Keyset Pagination
A pagination method that queries indexed column boundaries (WHERE (date, id) > (:d, :id)) to achieve constant O(1) page retrieval.
\n
Lock Escalation
A database mechanism (SQL Server) that converts many fine-grained row locks into a single Exclusive Table Lock to save lock memory.
\n
Multi-Version Concurrency Control (MVCC)
A concurrency mechanism that maintains snapshot tuple versions so that readers never block writers and writers never block readers.
\n
Nested Loops Join
A join algorithm that iterates through outer rows and performs an inner index seek for each row, optimal for small outer driving tables.
\n
Non-Clustered Index
A secondary index structure containing sorted keys and bookmark row pointers back to the base table.
\n
Number of Distinct Values (NDV)
The count of unique distinct values in a column, used to compute column density and selectivity.
\n
Parameter Sniffing
When the optimizer compiles and caches a plan based on the parameter values passed during first execution, risking plan regressions on skewed data.
\n
Partition Pruning
A storage optimization where the engine skips reading non-qualifying partition files/sub-tables based on query WHERE predicates.
\n
Predicate Pushdown
A rule-based optimization that moves filter predicates down the operator tree to eliminate rows before joins and aggregations.
\n
Projection Pushdown
A rule-based optimization that prunes unreferenced columns from the plan to minimize memory bandwidth and I/O.
\n
Read Committed Snapshot Isolation (RCSI)
An isolation mode in SQL Server that uses TempDB row versioning for Read Committed, eliminating read shared locks.
\n
SARGable
Search-Argument-Able: predicates structured so that the engine can use B-Tree index seeks rather than full scans.
\n
Selectivity
The fraction of rows in a table that satisfy a filter predicate (Selectivity = Matching Rows / Total Rows).
\n
Sort-Merge Join
A join algorithm that advances cursors along two pre-sorted input streams in lockstep, optimal for pre-ordered inputs.
\n
Table Bloat
Dead tuple accumulation in PostgreSQL MVCC tables resulting from heavy updates and lagging Autovacuum cleanup.
\n
Tipping Point
The selectivity threshold (typically 1% to 5%) where random I/O from index lookups becomes slower than sequential table scanning.
\n
Top-N Sort
An optimized sorting operator for ORDER BY ... LIMIT K queries using an in-memory priority queue of size K.
\n
Volcano Iterator Model
A classic demand-driven query execution model where operators implement open(), next(), and close() interfaces.
\n
Write-Ahead Log (WAL)
An append-only disk transaction log where changes are recorded before being written to data pages, ensuring Durability (ACID).
